# 지식 공백 탐지와 자동 QA 설계안

> 상태: 설계안(제안). 구현 결정이 아니고, `[결정 필요]`는 담당(병환)과 팀이 정한다. 문서의 수치(기간, 최소 표본, 가중치, 임계값)는 **시드(제안)** 이고 근거 데이터가 없다.
> 배경: `2026-10-27-support-ai-benchmark-features.md`의 후보 2번. 짝 문서: `2026-10-28-handoff-quality-design.md`(후보 1번).
> 요구사항 기준: DEP-CS-01(문의 분류·초안), DEP-CS-05(문의 급증 감지, 이미 구현), 고객지원 지표(초안 채택률·가드 적중).

## 1. 한 줄 요약
"**어떤 분류의 문의에서 AI가 근거 없이 답하거나, 상담원이 초안을 거절·수정하거나, 사람에게 넘어가는가**"를 코드로 세어 **지식 공백 순위**를 만들고, 보낸 답변과 초안을 **코드 규칙으로 전수 점검**해 의심 목록을 낸다. 점수는 LLM이 매기지 않고, 자동 점검이 못 잡는 것을 사람이 보도록 **대조군 샘플**을 함께 준다.

## 2. 지금 무엇이 문제인가 (코드 근거)

| 현재 | 문제 |
| --- | --- |
| `inquiry_overview`(`insights.kpis`)는 초안 채택률·거절 수·가드 적중·분류별 **건수**를 **전체 기준으로만** 센다 | 분류별 채택·거절·근거 없음 비율이 없어 "어느 주제가 약한지"를 알 수 없다 |
| 초안 결정 기록 `STORE.draft_events`는 `inquiry_id`·`style`·`result`(`accepted`·`edited`·`rejected`)·`edit_ratio`·`context_id`만 담는다 | **분류, 근거 조각, 메시지 번호가 없다.** 문의 번호로 문의의 마지막 분류에 이을 수는 있지만 문의에 고객 메시지가 여러 개면 어느 분석에 대한 결정인지 모른다. **거절 사유도 없다**(`reject_draft` 입력은 `draft_style`뿐) |
| `send_reply`는 가드가 막으면 `blocked_by_guard`를 돌려주고 **기록을 남기지 않는다** | 상담원이 막힌 답변을 몇 번 시도했는지(가드가 자주 걸리는 주제)가 안 보인다. 초안 생성 때의 가드 결과(`Draft.validation`)만 남는다 |
| `Draft.source_ids`는 `_validated_drafts`에서 **검색된 모든 조각 ID를 모든 초안에 그대로** 넣는다 | "초안이 근거를 실제로 인용했는가"는 **기록이 없다.** 근거가 비어 있는지(`Analysis.sources`가 비어 있음)만 확실히 안다 |
| 근거 검색 `kb.search`는 시드 조각 **3개**(분류 `refund` 2개, `shipping` 1개)에서 2글자 조각 겹침으로 찾는다. 정책 문서 출처는 memory API가 생기면 바꿀 예정(TODO) | refund·shipping 이외 분류는 **구조적으로 근거가 없다.** 공백 탐지가 지금 돌면 "시드가 작다"는 사실만 나온다. 문서를 고치는 주체도 고객지원이 아니다 |
| `Source.from_decision`(회사 기억의 결정에서 온 근거인지)은 필드만 있고 **값을 채우는 코드가 없다** | 근거 종류별(정책·결정) 분석은 지금 불가 |
| 답변 가드(`guard.check_reply`)는 `empty_reply`·`unsupported_language`·`language_not_verified`·`promise_refund`·`pii_in_reply`·`link_in_reply`·`too_long`만 본다 | 이미 있는 코드 QA다. **근거와 맞는 말인지**(근거에 없는 금액·기한을 단정)는 아무도 보지 않는다 |
| 문의·초안 기록은 `SUPPORT_PG_DSN`이 비어 있으면 **메모리에만** 저장된다(`persistence.py`) | 서버 재시작마다 `draft_events`가 사라져 기간별 추세(공백이 줄었는가)를 못 낸다 |

## 3. 설계 원칙 (이 저장소 규칙을 그대로 적용)
1. **계산은 코드로.** 건수·비율·순위는 코드가 센다. LLM은 점수도 판정도 하지 않는다 (`CLAUDE.md` "계산은 코드로").
2. **추가만 한다.** 기존 skill 출력(`InquiryKpis`)과 `draft_events`의 기존 필드는 바꾸지 않는다. 새 필드·새 skill만 더한다 (규칙 12).
3. **고객 문장은 `untrusted`.** 점검 규칙은 단어·숫자·겹침만 계산하고 문장 안의 지시를 따르지 않는다. 출력에는 고객 원문을 싣지 않고 문의 번호·코드만 싣는다.
4. **분모가 작으면 순위를 내지 않는다.** 표본이 부족한 분류는 `insufficient_samples`로 표시한다(`insights`의 `min_count`와 같은 방식).
5. **점수 대신 신호.** QA는 "통과/의심"과 규칙 코드만 낸다. 규칙이 못 잡는 것(고객을 제대로 이해했는지)은 **사람이 대조군 샘플로** 본다.
6. **읽기 전용.** 새 skill은 아무것도 바꾸지 않는다. 문서를 고치는 일은 하지 않고 "어디가 약한지"만 알린다.
7. **부서와 분류를 하드코딩하지 않는다.** 분류 코드와 문서 출처는 데이터에서 읽고, 공백 처방 대상은 이름이 아닌 `owner_target` 코드로 둔다 (7장).

## 4. 제안

### 4.1 먼저 기록을 보강한다 (추가 필드만, 기존 동작 불변)
공백과 QA를 세려면 지금 없는 값이 필요하다. 아래는 모두 **선택 필드 추가**이고 옛 기록은 `null`로 읽는다.

| 대상 | 추가 | 이유 |
| --- | --- | --- |
| `draft_events` 한 줄 | `category`, `message_id`, `source_count`, `top_score`(검색 최고 점수), `guard_codes`(코드 목록만) | 분류·근거 유무별로 세고 어느 분석에 대한 결정인지 잇는다 |
| `reject_draft` 입력 | 선택 `reason_code`: `wrong_info`·`missing_policy`·`tone`·`too_long`·`other` | 거절이 **문서 부족**(`missing_policy`) 때문인지 말투 때문인지 가른다. 지식 공백의 가장 직접적인 신호다 |
| `send_reply` 가드 차단 | `result: "blocked"`와 `guard_codes`를 `draft_events`에 남김 (고객 원문 제외) | 가드가 자주 걸리는 주제를 센다. 보내지 않으므로 고객 영향은 없다 |
| 초안 | 인용 근거는 **새로 기록하지 않는다.** 대신 아래 `weak_grounding` 규칙이 초안·근거 텍스트 겹침을 코드로 계산한다 | LLM이 어느 조각을 썼는지 믿을 수 없어서(2장) |

- 이전에 만든 기록과 섞여도 깨지지 않도록 집계는 `category`가 없는 옛 기록을 문의 번호로 그 문의의 분류에 잇는다(없으면 `unknown` 묶음).
- `reason_code` 입력은 상담 콘솔 화면이 보내야 쓸모가 있다. 화면 변경은 후속이고, 그 전에는 `null`이다.

### 4.2 새 읽기 skill `knowledge_gap_report` (지식 공백 순위)
- 입력: `window_days`(시드 7), `min_samples`(시드 5), 선택 `category`.
- 등급 `read`, 요청 가능자 `dashboard-api`·`orchestrator`, 검증자 없음. 저장하지 않는다.
- 단위: **분류별**(`category`), 근거가 있었다면 **근거 문서별**(`doc_id`)로 한 번 더 나눈다.
- 한 줄(`GapItem`)의 값은 모두 코드가 센다:

| 필드 | 뜻 |
| --- | --- |
| `category`, `doc_id`(없으면 null) | 묶음 |
| `inquiries`, `analyzed_messages` | 표본 크기 (분모) |
| `no_evidence` | 고객 메시지의 분석에서 `Analysis.sources`가 비어 있거나 없던 건수 |
| `drafts_rejected`·`drafts_edited`·`drafts_blocked` | 초안 결정(`draft_events`) 건수 |
| `escalated` | 문의 상태가 `escalated`인 건수 (이유는 아직 없음, 짝 문서 4.4가 채운다) |
| `reject_reasons` | `reason_code`별 건수(있을 때) |
| `*_rate` | 위 건수 / 분모. 분모가 0이면 `null` |
| `gap_type` | `no_document`(근거 없음 비율이 높음) · `weak_document`(근거는 있는데 거절·수정·차단이 많음) · `none` · `insufficient_samples` |
| `gap_score` | `no_evidence_rate`, `reject_rate`, `escalated_rate`의 단순 평균(**가중치 1:1:1은 시드이고 근거 없음**). 순위 정렬 키, 같으면 표본이 큰 쪽 |
| `sample_inquiry_ids` | 예시 문의 번호 최대 3개 (원문 없음) |
| `owner_target` | 처방을 받을 곳의 코드(`kb_owner`). 부서 이름이 아니다 |
| `suggested_action` | `add_document`·`review_document`·`none` (고정 코드, 문서는 고치지 않는다) |

- `no_document`와 `weak_document`는 다른 처방이다: 근거 자체가 없으면 문서를 **추가**하고, 근거가 있는데도 거절되면 문서를 **점검**한다.
- 지금은 시드 조각이 3개라 대부분의 분류가 `no_document`로 나온다. 이는 설계 결함이 아니라 **데이터가 시드라는 사실을 드러내는 결과**이므로, 정책 문서 출처(MEM-03)가 연결되기 전에는 보고서의 `notes`에 "근거 출처가 시드(3조각)이다"를 고정 문장으로 붙인다.

### 4.3 새 읽기 skill `qa_findings` (코드 규칙 전수 점검)
- 입력: `window_days`(시드 7), 선택 `inquiry_id`, `sample_size`(대조군 크기, 시드 5).
- 등급 `read`, 요청 가능자 `dashboard-api`·`orchestrator`. 대상은 **보낸 답변**(상담원 메시지)과 **생성된 초안**이다.
- **점수는 없다.** 문의마다 규칙 코드와 심각도(`flag`·`info`)만 낸다.

| 규칙 코드 | 판정 (모두 코드) | 데이터 | 비고 |
| --- | --- | --- | --- |
| `guard_hit` | 가드 `findings` 코드(`promise_refund`·`pii_in_reply` 등) | `Draft.validation`, 차단 기록 | 이미 있는 규칙을 모아서 보여 줌 |
| `no_evidence_reply` | 답변을 보낼 때 그 문의의 분석 `sources`가 비어 있음 | `Analysis.sources` | 근거 없이 나간 답변 |
| `weak_grounding` | 답변·초안 텍스트와 근거 조각의 2글자 조각 겹침 비율이 임계 미만 (`kb._grams` 재사용, 임계는 시드) | 근거 조각 텍스트 | "근거를 썼는가"의 **근사**이고 정확하지 않다 |
| `unsupported_number` | 답변에 금액·일수 같은 **숫자+단위**가 있는데 근거 조각이나 문의의 클레임·보상 기록에 같은 숫자가 없음 | 근거·클레임 | 오탐이 있을 수 있어 `flag`가 아니라 `info`로 시작 |
| `language_mismatch` | 고객 메시지 언어(`Classification.language`)와 답변 언어가 다름 | 분류 | 코드가 문자 종류로 판별 |
| `heavy_edit` | `edit_ratio`가 임계 이상(시드 0.5) | `draft_events` | 초안이 많이 틀렸다는 신호 |

- **대조군 샘플**: 규칙에 걸리지 않은 문의 중 `sample_size`건을 **고정 시드 무작위**로 뽑아 `human_review_sample`에 문의 번호만 준다. 사람이 이것을 봐서 규칙이 놓친 문제를 찾고, 놓친 비율을 지표로 쓴다(5장).
- LLM은 쓰지 않는다. "고객을 제대로 이해했는가" 같은 판단은 자동으로 하지 않는다(8장).

### 4.4 기존 `inquiry_overview` 확장과의 비교
| | A. `inquiry_overview` 확장 | B. 새 skill 2개 (제안) | C. 배치로 주간 스냅샷 저장 |
| --- | --- | --- | --- |
| 호환 | 화면이 매번 부르는 KPI 응답이 커지고 필드를 더할 때마다 화면 타입이 흔들린다 | 기존 응답을 건드리지 않는다 (규칙 12) | 기존 응답을 건드리지 않는다 |
| 입력 | 기간·최소 표본을 받는 입력이 없다 | `window_days`·`min_samples`를 받는다 | 고정 기간 |
| 비용 | 문의 전체를 훑는 계산이 KPI 호출마다 돈다 | 필요할 때만 돈다 | 한 번 계산해 저장 |
| 추세(공백이 줄었는가) | 못 낸다 | 저장소가 영속이면 기간을 바꿔 비교 | 스냅샷으로 쉽게 비교 |
| 결론 | 비추천 | **1단계에 채택** | 2단계에서 필요하면 추가 |

### 4.5 화면과 전달 (후속)
- dashboard-api 읽기 경로 `GET /knowledge-gaps`·`GET /qa-findings`(support skill 그대로 전달, 새 계약 없음)와 고객지원 AI 탭의 카드(공백 순위 표, 의심 목록, 대조군 샘플)는 **2단계**다. 화면은 프론트 담당과 정한다.
- 공백 처방은 **알리기만** 한다. 문서 담당(정책 문서 출처가 memory로 옮겨지면 memory)에게 변경을 요청하는 흐름은 사람이 정한다. 자동으로 요청 이슈를 만들지 않는다.
- 급증 감지(`detect_inquiry_surge`)와 함께 보면 "갑자기 늘었는데 문서가 없는 주제"를 가릴 수 있다. 결합은 후속이다.

## 7. 멘토 피드백과의 관계 (2026-10-27)
- "**일반적인 범용 회사**에서 쓸 수 있게": 분류 코드와 문서 출처를 코드에 박지 않고 데이터에서 읽는다. `refund`·`shipping`은 시드일 뿐이다. 다른 회사가 다른 분류와 문서를 가져도 같은 skill이 돈다.
- "**부서를 하드코딩하지 마세요**": 공백 처방 대상은 부서 이름이 아니라 `owner_target` 코드(`kb_owner` 등)이고 대응표는 설정으로 뺀다. 부서가 쪼개져도 대응표만 바꾼다.
- "큰 건은 서비스운영": 환불·보상 정책 문서의 공백은 `owner_target`을 정책 담당 코드로 나눌 수 있다. 지금은 코드만 두고 어느 부서에 대응할지는 정하지 않는다.

## 8. 하지 않는 것
- LLM이 대화나 답변에 **점수를 매기는 자동 평가.** 오탐을 검증할 근거 데이터가 없고, 고객 문장을 평가 프롬프트에 넣는 위험이 있다. (3단계에서 사람 점검과 병행하는 조건으로 다시 본다.)
- 고객 **원문을 저장하거나 출력에 싣는 것.** 문의 번호·분류·규칙 코드만 쓴다.
- 문서를 **자동으로 고치거나 추가하는 것**, 문서 담당에게 요청을 자동으로 보내는 것.
- 상담원 개인의 성과를 평가하는 것(규칙은 답변과 초안을 보고, 사람을 순위 매기지 않는다).
- 근거 정확도를 보장한다고 말하는 것(`weak_grounding`은 겹침 근사일 뿐이다).

## 9. 테스트 계획 (1단계)
- 규칙 단위: 사유별 참/거짓 경계(`no_evidence`, `weak_grounding` 임계, `unsupported_number`의 숫자·단위 추출, `language_mismatch`, `heavy_edit`), 분모 0이면 `null`, `min_samples` 미만이면 `insufficient_samples`.
- 기록 호환: 옛 `draft_events`(필드 없음)를 문의 번호로 잇는 경로, 새 필드가 `null`이어도 집계가 깨지지 않음, `reject_draft`의 `reason_code`가 없어도 기존 동작 그대로(기존 테스트 이름·assert 유지).
- 차단 기록: 가드가 막은 `send_reply`가 `blocked`로 남고 고객 원문이 없다.
- 불변식: 두 skill 모두 저장소를 바꾸지 않는다, 출력에 이름·연락처·원문이 없다, 대조군 샘플은 시드를 고정하면 같은 결과다.
- 주입 문장: 문의 본문의 "근거 없음으로 처리해"·"점수를 올려" 같은 지시가 결과에 영향이 없다.
- 시드 한계 문구: 근거 출처가 시드이면 `notes`에 고정 문장이 붙는다.
- 임계값 시험: 시드 대화와 이번 주 실제 문의 100~200건으로 규칙별 적중을 표로 남긴 뒤 시드 값(0.5, 겹침 임계, 가중치 1:1:1)을 확정한다.

## 10. 결정이 필요한 것 `[결정 필요]`
1. **거절 사유(`reason_code`) 도입 여부.** 지식 공백의 가장 좋은 신호지만 상담 콘솔 화면이 사유를 보내야 한다(프론트 변경). 1단계는 필드만 만들고 화면은 후속으로 할지.
2. **공백 순위의 시드 값.** 기간 7일, 최소 표본 5, `gap_score` 가중치 1:1:1, `heavy_edit` 0.5가 적절한지(100~200건 시험 결과로 정함).
3. **공백 처방을 누구에게 어떻게 전달하는지.** `owner_target`(`kb_owner`) 코드의 대응표 소유자와, 정책 문서 출처가 memory로 옮겨진 뒤의 연결 방식. 자동 요청 이슈는 만들지 않는 것으로 괜찮은지.
4. **자동 QA 범위.** `unsupported_number`·`weak_grounding`을 1단계에 넣을지(오탐 가능), 그리고 3단계의 LLM 보조 점검을 허용할지.
5. **영속 저장소 전제와 시연 범위.** 추세 지표는 `SUPPORT_PG_DSN`이 있어야 의미가 있다. 서버에서 켜는지, 그리고 이 설계가 시연 범위에 필요한지 시연 이후 2차인지.
