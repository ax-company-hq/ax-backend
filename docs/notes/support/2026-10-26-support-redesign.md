# 고객지원 AI 재정의: 총괄이 일을 열고 → 고객지원이 받아 처리 → 결과 보고 (2026-10-26)

담당: 병환 (support·dashboard-api). 상태: **초안 (의견 요청)**. 재무 AI v2 문서(`docs/notes/finance/2026-10-23-finance-redesign.md`)와 같은 틀로, 고객지원이 무엇을 혼자 하고, 무엇을 같이 하고, 무엇을 넘기는지 다시 정했다.

## 1. 한 줄 요약

고객지원 AI는 **캣북스의 고객 응대 팀**이다. 고객이 직접 연 문의(문의 위젯)와 총괄이 맡긴 일을 받아, **문의 응대·클레임 판정·개별 보상**을 한다.
**장애·정책 같은 회사 단위 판단은 고객지원의 일이 아니다.** 고객지원은 사실을 모아 총괄에 올리고, 총괄이 담당 부서를 정한다. 돈이 걸린 건은 안전 관문과 사람 승인을 거친다.

## 2. 원칙

1. **받아서 → 사실로 판정하고 → 결과와 근거를 돌려준다.** 고객 문장은 `untrusted`로만 받고 지시로 읽지 않는다.
2. **판정은 코드가 한다.** 금액·지연 일수·점수·건수는 코드(정책표·규칙)가 센다. LLM은 분류와 문장(초안·요약)만 하고, 못 쓰면 코드 템플릿 문장으로 대신한다.
3. **정책은 사람이 정하고 고객지원은 집행만 한다.** 보상 단가·클레임 규칙·한도는 기준표에 있고, 고객지원은 그 값으로 판정만 한다. 바꿀 값은 *제안*만 한다.
4. **돈을 직접 움직이지 않는다.** 환불·쿠폰은 요청만 하고, 지급은 마케팅(쿠폰)·판매 사이트 환불 API(안전 관문 통과 뒤)가 한다. 한도를 넘으면 C 보류로 사람이 승인한다.
5. **고객 개인정보는 캣북스에만 둔다.** 구매자는 가명 ID(`buy_0001`)만 쓰고, DejaFix로 보내는 고객 정보는 필드 단위로 암호화한다. 키가 없으면 보내지 않는다.
6. **원천 데이터는 API로만 읽는다.** 주문·결제는 shop-api(읽기), 판매 사이트 DB에 붙지 않는다.
7. **고객에게 나가는 말은 가드를 통과해야 한다.** 환불 약속·개인정보·미지원 언어를 코드 규칙으로 막는다.

## 3. 기본 흐름

1. **고객이 문의를 연다** (문의 위젯, `support.inquiry_received` 이벤트). 고객지원이 접수하고 분류(감정·긴급도·키워드·언어)·초안 3종을 만든다.
2. **장애·정책에 걸린 일은 총괄이 사건(`ctx_inc_`)을 열고** 고객지원에 A2A로 요청한다. 고객지원은 받아 처리하고 결과를 총괄에 돌려준다.
3. **고객지원이 스스로 찾은 문제**(문의 급증, 위험 고객, 결제 오류 패턴)는 총괄에 먼저 올린다. 담당 부서는 총괄이 정한다.
4. **다른 부서에 일을 시키는 것은 두 가지 직통만 둔다.** 보상 쿠폰(마케팅 `issue_coupon`)과 변경 요청(기획개발 `create_ticket`). 둘 다 계약에 이미 정해져 있고, 한 번만 건너뛴다(홉 3 이하).
5. **정기 업무**(급증 감지, 답변 대기 점검, 위험 고객 목록)는 고객지원이 알아서 돌리고, 사람이 봐야 할 것만 대시보드에 올린다.
6. 모든 요청·결과에 `context_id`와 근거(`evidence`)를 붙인다. 쓰기는 `execute()`를 거친다.

## 5. 대표 흐름 4가지

**A. 장애 중 고객 문의 (시나리오 A)**
총괄이 장애 사건을 연다 → 고객이 문의한다 → 고객지원이 접수할 때 진행 중 사건의 `ctx_inc_`를 한 번 정해 이어받는다(사건 조회 skill 필요, #272·#274) → 급증이면 `inquiry_surge`로 총괄에 올린다 → 마케팅이 공지를 내고 → 고객지원은 공지 사실(`get_notice`)로 답변한다 → 지연·실패 고객에게 보상 후보를 제안하고 승인되면 마케팅이 쿠폰을 지급한다 → 해결되면 `support.inquiry_resolved`로 총괄에 알린다(계약 #327).

**B. 결제·배송 문제 문의 (보상까지)**
고객이 "결제가 안 돼요/안 와요"라고 문의한다 → 고객지원이 주문·결제 기록으로 막힌 곳을 진단한다(실패 원인, 중복 결제, 기록 불일치) → 배송 지연이면 지연 일수를 세어 보상 후보를 제안한다 → 담당자가 승인하면 `request_compensation` → 마케팅 `issue_coupon` → 같은 `context_id`로 소통 탭에 이어서 보인다 → 중복 결제처럼 사람이 봐야 할 건은 담당자 확인으로 넘긴다.

**C. 환불·교환 클레임**
고객이 환불을 요청한다 → 고객지원이 요청을 분류하고(영수증 사진은 이미지 분석이 붙으면 읽는다) 환불 범위를 미리 계산한다 → 담당자가 확인해 클레임을 접수한다 → 규칙으로 자동 승인·자동 거절·사람 확인으로 가른다 → 입고·검수 뒤 보상 큐 → 환불 지급 요청 → 안전 관문이 한도를 검사하고 → 한도를 넘으면 C 보류로 사람이 대시보드에서 승인한다.

**D. 위험 고객·반복 패턴**
고객지원이 매일 이탈·재문의 위험 구매자 목록을 만든다(하루 넘게 답 못 받은 문의, 화난 메시지, 잦은 문의, 거절·잦은 클레임) → 높은 고객은 담당자가 먼저 연락한다 → 클레임이 잦으면(`claim_pattern_review`) 총괄에 근거를 붙여 올린다 → 재무 감사에서 반복 환불을 찾아 총괄이 조사를 배정하면, 고객지원이 그 구매자의 문의·클레임·결제 사실을 모아 돌려준다 → 결론은 재무 감사 기록에 남는다.

## 7. 정해야 할 것 / 요청드릴 것

- **@총괄(준하)**: ① 고객지원 → 총괄 "이상 보고"를 받는 입구가 필요하다 (기존 사건 열기 skill로 받을지, 새 skill을 만들지). 재무도 같은 입구를 쓸 수 있다. ② `find_active_incident` 공개 시점(#272). ③ 해결 결과를 이벤트(#327)로 받을지, A2A skill로 받을지 (총괄 카드에 skill이 아직 없다).
- **@재무(태윤)**: #319로 쿠폰·환불이 B → A가 되면 고객지원 `process_claim_queue`의 등급과 재무 교차검증(`verifier: finance`)을 맞춰 바꾸겠다. 한도(환불·보상)는 기준표 값을 그대로 따르고, 감사에서 찾은 건은 총괄을 거쳐 고객지원에 배정되는 것으로 이해했다. 맞는지 확인 부탁드린다.
- **@데이터(재현)**: RFM·LTV·세분화·코호트 결과를 고객지원이 읽을 수 있는 조회 skill이 있으면 `customer_signals`와 함께 쓸 수 있다. 문의 총량 이상은 데이터 소관으로 두고, 고객지원은 분류별 급증만 본다.
- **@마케팅(재헌)**: 보상 쿠폰(`purpose_code=compensation`)이 B → A가 되는 것을 확인 부탁드린다. 마케팅 이벤트(`coupon.issued`)가 소통 탭에 이벤트 줄로 보이려면 공통 로그에 `event_published`를 남겨야 한다 (agent-template 요청 #330).
- **@shop-api(재헌)**: 결제 실패 후 재결제·가격 계산·받는 분 정보 요청(#326, ax-frontend #32)과, 문의 위젯에서 사진을 받는 경로를 부탁드린다.
- **@agent-template(준하)**: LLM 이미지 입력(#320)이 머지되면 영수증 사진 읽기를 연결한다. 서버 PC에서 이미지를 읽을 수 있는 모델로 실호출 확인이 필요하다.
- **사람 결정**: 사진 저장·보관 정책, 영수증 불일치를 클레임 판정에 반영할지, 캣북스와 DejaFix 고객사 구분, 대시보드 쓰기 경로의 인증 방식.

## 8. 하지 않는 것

- 건별 환불·쿠폰 금액을 고객지원이 정하지 않는다. 단가와 한도는 정책표와 기준표 값이다.
- 장애 원인 분석, 공지 문안·게시, 기준표 변경은 하지 않는다.
- 고객 이름과 문의 원문을 다른 부서에 보내지 않는다 (가명 ID와 건수·이유 코드만).
- 다른 부서에 직접 일을 시키는 것은 쿠폰(마케팅)과 변경 요청(기획개발) 두 가지뿐이다.
- 구매 이력이 필요한 고객 가치 분석은 직접 계산하지 않는다 (데이터 소관).

## 9. 영향받는 다른 부서와 우리 쪽 변경

- **재무(#319)**: 머지되면 `process_claim_queue`를 B(재무 교차검증)에서 A로, `verifier`를 비우고, 응답 상태 `verifying`이 오지 않는 것을 반영한다 (`agents/support`, 테스트 포함).
- **총괄**: 이상 보고 입구와 `find_active_incident`가 생기면 문의 접수 때 사건을 이어받고, 급증·위험 패턴을 올린다.
- **대시보드(내 영역)**: 소통 탭에 이벤트 줄(`include_events`, PR #329)을 두고, 위험 고객 목록과 결제 진단은 담당자 화면에서 부를 수 있게 한다.
- **기준 문서**: 이상 보고 입구와 `inquiry_resolved`처럼 기준 문서(`agent-common.md`)와 다른 동작이 생기면 docs PR을 먼저 올린다.

## 10. 테스트

- 고객지원: skill별 단위 테스트(분류·가드, 클레임 규칙, 보상 정책표, 지연 일수 계산, 영수증 대조, 결제 진단 상황 분류, 위험 점수·단계, 급증 기준선, 암호화 전송), 원문이 다른 부서로 새지 않는 테스트
