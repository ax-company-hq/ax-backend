# 인사 화면 프론트엔드 인계 자료

대상: 화면 담당(ax-frontend `dashboard-web`). 짝 문서: `dashboard-api-contract.md`(API), `dashboard-fixtures/`(응답 샘플).
시안: hr 개발용 데모(`uv run --package ax-agent-hr python -m hr_agent.demo` → http://localhost:8114, 소스 `agents/hr/src/hr_agent/demo/page.html`). 데모는 개발 전용이고 **디자인이 아니라 흐름·문구·상태의 기준**이다.

## 1. 만들 화면 6개 (인사 탭 안)

| # | 화면 | 하는 일 | 쓰는 API (`/api/dashboard/hr/...`) | 데모의 같은 탭 |
|---|---|---|---|---|
| 1 | 인수인계 | 진행 중 인수인계와 빈 칸 질문, 답하기 | `GET handovers`, `GET questions`, `POST questions/{id}/answer` | 4 인수인계 |
| 2 | 변경(발령·퇴직·입사) | 요청 상태와 확인 목록 | `GET changes` | 5 발령·퇴직 (조회 부분) |
| 3 | 온보딩 | 읽을 카드 순서, 진행률, 단계 완료 | `GET onboardings`, `POST onboardings/{id}/steps/{step_id}` | 6 온보딩 |
| 4 | 명부·교대 | 영역별 담당, 공백 영역 | `GET roster` | 3 명부·교대 |
| 5 | 후보 카드 큐 | 확신 낮은 카드 승인·폐기 | `GET candidate-cards`, `POST candidate-cards/{id}/decision` | 1 기록(후보 카드의 승인·폐기 버튼) |
| 6 | 사건의 "hr이 한 일" | 시간순 기록 | `GET audit/{context_id}` | 감사 로그 |

보류 큐(퇴직 확정·미달 인수인계 승인)는 **인사 탭이 아니라 기존 C 보류 큐 화면**(safety)에서 한다. 인사 탭 홈에는 건수만 링크로 보여 주면 된다.
(선택) 계획 비교 화면(`POST plan-check`)은 필수 범위 밖이다.

## 2. 화면별 명세

### 2-1. 인수인계
- 목록 카드 한 장 = `HandoverView` 하나: 인계자 → 후임, 영역, **상태 배지**, **완성도**(막대 + "N%", 숫자는 그대로), 인계 목록, 빈 칸 질문.
- 상태 배지: `input_required` 주황 "질문 대기", `ready` 초록 "확정 가능", `confirmed` 초록 "확정", `held` 주황 "승인 대기(보류 큐)", `draft` 회색.
- 완성도 80% 미만이면 "확정 요청하면 보류 큐로 간다"고 안내한다(기준값은 서버 설정이라 숫자를 화면에 하드코딩하지 않는다. 안내 문구만).
- 항목 `kind` → 아이콘/라벨: `pr` PR, `ticket` 티켓, `deployment` 배포, `decision` 결정, `document` 문서, `other` 기타. `source_ref`는 복사 가능한 작은 글씨.
- **질문과 답하기**: 질문 문장을 그대로 보여 주고(`gap_field`는 필드 이름이라 라벨로만), 입력칸 + `답변 보내기`. 보낼 때 `idempotency_key`를 만들어 함께 보낸다(버튼 한 번 누를 때마다 새 키, 재시도할 때는 같은 키). 성공하면 목록을 다시 불러온다. 409(`CONFLICT`)면 "이미 다른 답이 반영된 질문입니다"를 보여 준다.
- `(다시 묻습니다 N번째)`로 시작하는 질문은 강조 표시한다(답이 늦어진 것).
- 빈 상태: "진행 중인 인수인계가 없어요."

### 2-2. 변경(발령·퇴직·입사)
- 한 줄/카드 = `ChangeView`: 종류(발령·교대·퇴직·입사), 대상자 → 후임, 영역, 상태, 확인 목록(체크 표시는 읽기 전용).
- 상태 라벨: `requested` 요청됨, `confirmed` 재배치 확정, `offboarded` 퇴직 완료, `cancelled` 퇴직 취소, `expired` 만료(오래 방치돼 닫힘). 퇴직 `confirmed`는 "퇴직 확정 대기"로 보여 준다(사람 승인은 보류 큐).
- 변경을 요청·확정하는 버튼은 **만들지 않는다**(통합 에이전트 몫).
- 확인 목록의 `권한 …` 항목은 "각 부서가 실행하는 일"이라는 설명을 붙인다(hr은 권한을 직접 바꾸지 않는다).

### 2-3. 온보딩
- `OnboardingView`: 새 담당자, 영역, **진행률**(`progress`), 단계 목록(순서·제목·읽을 카드 ID·완료).
- 단계 오른쪽 `완료 표시`/`되돌리기` 버튼 → `POST .../steps/{step_id}` `{done: !done}`. 성공 응답이 갱신된 단계와 진행률 전체이므로 그대로 반영한다(화면이 진행률을 계산하지 않는다).
- 읽을 카드가 없다고 나온 온보딩은 "읽을 결정 카드가 아직 없어요"를 보여 준다.

### 2-4. 명부·교대
- 영역마다 카드: 담당(`owner`)·예비(`backup`)와 교대 시각(UTC → 화면은 KST로 바꿔 표시, 규칙).
- `gap_areas`에 있는 영역은 빨간 "담당 공백" 배지. 담당이 아예 없는 영역은 "담당 없음", 교대 시각에 비는 영역은 "교대 공백"이다(응답은 둘을 합친 목록이므로 `entries`에 담당이 없으면 "담당 없음", 있으면 "교대 공백"으로 구분).
- 개인 정보 없음: `member_id`(`emp_xx`)만 보인다.

### 2-5. 후보 카드 큐
- 카드 = 계약 `Card`: 제목, 종류, **확신도 배지**(`low`·`mid`·`high`만, 퍼센트 금지), 영역(`extra.area`), 결정·이유·검토한 대안(`body`), 근거 참조.
- `이유: 확인할 수 없음`처럼 서버가 보낸 문구는 그대로 보여 준다(빈칸·0으로 바꾸지 않는다).
- 버튼: `승인(확정)` / `폐기` + 메모(선택). 승인하면 카드가 `active`가 되고 같은 영역의 옛 결정이 대체될 수 있다 → 성공 후 큐를 다시 불러온다. 이미 처리됐으면 409(`NOT_CANDIDATE`)이므로 "이미 처리된 카드입니다"를 보여 주고 새로고침.

### 2-6. 사건의 "hr이 한 일"
- `AuditEntry[]`를 `seq` 순서로: 번호, 시각(KST), 종류 라벨, 내용(JSON은 접어서 펼쳐 보기).
- 종류 라벨 표는 데모 `page.html`의 `AUDIT_LABEL`을 그대로 쓰면 된다(모르는 종류는 원문 `kind`를 보여 준다).
- 기록이 없으면 "기록이 없어요"(이 사건에서 hr이 한 일이 아직 없다는 뜻).

## 3. 공통 규칙 (루트 `CLAUDE.md`·안전 규칙과 같다)
- **값이 없으면 "확인할 수 없음"** + 조회 시각. `null`을 0이나 빈칸으로 그리지 않는다(`UnknownValue`).
- **확신도는 low/mid/high만**(퍼센트 금지). 완성도·진행률은 서버가 센 정수를 그대로 쓴다.
- **실행·승인 버튼을 마음대로 만들지 않는다.** 화면이 할 수 있는 사람 입력은 3가지뿐이다: 질문 답변, 온보딩 단계 완료, 후보 카드 결정.
- 키·토큰을 브라우저에 두지 않는다(JWT는 `sessionStorage`, 루트 규칙).
- 갱신은 **15초 폴링**(WebSocket 없음). 조회 시각(`collected_at`)을 "N분 전 기준"으로 보여 준다.
- 시각은 UTC 문자열로 오고 화면에서만 KST로 바꾼다.
- 오류 메시지는 서버의 `error.message`를 그대로 보여 준다(5장 오류 표).

## 4. MSW로 먼저 만들기
1. `docs/notes/hr/dashboard-fixtures/`의 파일을 핸들러 응답으로 쓴다. 이름 규칙: `GET_hr_handovers.json` → `GET /api/dashboard/hr/handovers`, `POST_hr_candidate-cards_decision.json` → `POST /api/dashboard/hr/candidate-cards/{id}/decision`.
2. 오류 화면은 `ERROR_*.json`(상태 코드가 파일 이름 앞부분)으로 만든다.
3. 파일은 실제 hr 출력이라 계약 모델과 정확히 같다. 코드가 바뀌면 `uv run python agents/hr/scripts/make_dashboard_fixtures.py`로 다시 만든다(테스트가 어긋남을 알려 준다).
4. 서버가 준비되면 MSW만 끄고 주소는 그대로 쓴다.

## 5. 데모에서 눌러 볼 순서(화면 설계 확인용)
1. 시나리오 탭 `전체 실행`으로 흐름 확인 → `1 기록`에서 "근거 없는 결정(후보)" 보내기 → 후보 카드의 `승인(확정)`/`폐기`.
2. `4 인수인계` → `초안 만들기` → 질문에 답하기 → 완성도가 오르는 것 → `확정 요청`(80% 미만이면 보류 큐).
3. `5 발령·퇴직` → 변경 요청 → 재배치 확정 → 보류 큐 승인(이 부분은 통합 에이전트·safety 몫).
4. `6 온보딩` → `완료 표시`로 진행률이 오르는 것.
5. 헤더 `+10분` → 보류가 10분 지나 자동 거절되는 것, 60분 지나면 질문이 "다시 묻습니다"로 바뀌는 것(시계를 움직여 확인).
